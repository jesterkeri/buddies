## Problem Statement

Buddies is a multi-agent productivity platform built on ElizaOS v2 with 5 specialized AI agents that coordinate autonomously. The project is competing in the Nosana Builders: ElizaOS Challenge ($3K USDC, deadline April 14, 2026). The demo needs to show judges that agent-to-agent coordination creates practical utility for developers, not just a chat interface.

Currently: Chief works, Bounty Hunter partially works, remaining agents untested. The startup standup system is wired but depends on the `hasApiKey()` fix (just completed). Provider-agnostic key system works with fetch patching for Vercel AI SDK v3.

## What Makes This Cool

The "zero to alive" moment: plug in one API key, watch all 5 agents wake up, run a standup, and start working together. Chief coordinates, Hawk reviews code, Radar researches, Bounty Hunter scans opportunities, Buddy checks wellness. They talk to each other autonomously. This is not a chatbot, it's a team.

The War Room Replay makes this coordination *visible*: a timeline view that lets judges scrub through agent-to-agent messages and see the team thinking together.

## Recommended Approach

**Approach B: Stabilize + War Room Replay**

The replay visualization is the forcing function that makes the coordination visible to judges. The data already exists in `.buddies-autonomous-messages.json`. The frontend work is a timeline component that reads from the existing `/autonomous-messages` endpoint on port 3001.

### Agent-to-Agent Chat (COMPLETED)

The frontend now displays agent-to-agent conversations in the main chat, not just agent-to-user messages. When Chief asks Hawk for a status update during standup, both the prompt and response appear in the chat room with agent colors. Format: "*(to Hawk)* Team standup..." followed by Hawk's response. This makes the coordination layer visible without needing a separate War Room component.

Additionally, the startup standup now triggers automatically when the first API key is connected (not just at boot). The config server calls `triggerStandupIfNeeded()` after saving a new key, so the "zero to alive" moment works: connect key -> agents wake up -> standup fires -> conversations appear in chat.

### Triage Rule

If agent stabilization is not complete by end of Day 1, fall back to Approach A (stabilize + polish only) and skip the replay component. A reliable demo with 5 working agents beats a flashy but broken replay.

### Key Mechanism: "One API Key" Flow

When a user sets one provider+key as the "default" in the settings page, it applies to all agents that don't have a per-agent override. The `getAgentAiConfig()` function falls back to `defaultProvider`/`defaultApiKey` when no per-agent config exists. So "plug in one key" means setting the default, which wakes up all 5 agents.

### Embedding Fallback

The codebase already has cross-agent embedding fallback in `ai-config.ts`. If a provider (e.g., Groq) doesn't support embeddings, `buildSecrets()` searches other agents' configs for a provider that does. If no embedding provider is available at all, the zero-vector safety net in `google-compat.ts` returns a fake 3072-dim vector so the agent doesn't crash. Day 1 must test the all-Groq scenario to verify graceful degradation.
